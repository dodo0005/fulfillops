# ADR-001: Postgres as the single source of truth, one transaction per order, leased jobs

- **Status:** Accepted
- **Date:** 2026-11-10 (decided at project start; consequences confirmed by evidence on 2026-11-20)
- **Deciders:** Person A (application), Person B (platform)

## Context

FulfillOps accepts orders for three products with fixed stock (KIT-100 ×7, PART-200 ×12,
PACK-300 ×5). The assignment requires, under real concurrency and failures:

1. Stock never goes negative and is never oversold, even when many buyers race for the last units.
2. The same `Idempotency-Key` sent 8 times at once, across 2 API replicas, creates **one** order
   and reserves stock **once**, and the same key still returns the same order after a restart.
3. A committed order is never lost, even if a worker is killed mid-job, and it is completed
   **exactly once**.
4. A job that keeps failing stops after a bounded number of retries and stays visible for review,
   with no automatic restock.

The API runs as two replicas and the worker as two replicas, so no guarantee can rely on memory
inside one process.

## Decision

**Postgres is the only source of truth.** Every invariant is enforced by a database constraint or
a conditional statement, never by a lock or a set kept in Python memory.

### 1. The transaction boundary: one transaction per accepted order

`api/orders_service.py::accept_order` does all of the following in **one** transaction, and the
API answers `202` only after it commits:

1. Read prices from `products` (never from the client) and compute `total_cents`.
2. Claim the key: `INSERT INTO orders ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING order_id`.
   - No row returned: the key exists. Same `request_hash` → return the existing `order_id`
     (replay). Different hash → `409 IDEMPOTENCY_CONFLICT`. Nothing is reserved either way.
3. Reserve stock, one statement per SKU, in **sorted SKU order**:
   `UPDATE inventory SET available = available - qty WHERE sku = ? AND available >= qty`.
   Zero rows updated → `409 OUT_OF_STOCK`, which rolls back the whole transaction.
4. Insert the aggregated `order_items` and exactly one `jobs` row (`status = 'queued'`).
5. Commit, then return `202 {"order_id", "status": "queued"}`.

Either the order, its stock reservation, its lines and its job all exist, or none of them do.

### 2. Constraints that enforce the invariants

| Invariant | Constraint (`db/migrations/001_init.sql`) |
| --- | --- |
| Stock never negative | `inventory.available CHECK (available >= 0)` |
| One order per idempotency key | `orders UNIQUE (idempotency_key)` |
| Same key + different payload is detectable | `orders.request_hash CHAR(64) NOT NULL` (SHA-256 of the JSON body with sorted keys) |
| One line per SKU per order | `order_items PRIMARY KEY (order_id, sku)` |
| One job per order | `jobs UNIQUE (order_id)` |
| An order completes at most once | `receipts PRIMARY KEY (order_id)` |
| Only valid states | `CHECK` on `orders.status` and `jobs.status` |

### 3. Jobs are claimed with a lease, not taken from a queue

Workers poll the `jobs` table every 2 s (`worker/claims.py::claim_next_job`):

- `FOR UPDATE OF j SKIP LOCKED` picks the oldest runnable job; rows another worker is claiming
  are skipped, so two workers never take the same job and never block each other.
- A claim sets `status = 'processing'`, `attempts = attempts + 1`, `locked_by = <worker id>`,
  `locked_until = now() + 20 s`.
- A job is runnable when it is `queued` and `next_attempt_at <= now()`, **or** when it is
  `processing` and `locked_until < now()` (its worker died: the lease expired).

Completion (`worker/processor.py::complete_order`) is one transaction that first re-checks
`locked_by = me AND status = 'processing'` with `FOR UPDATE`, then inserts the receipt
(`ON CONFLICT DO NOTHING`), sets the order `completed` and the job `done`.

Failure (`record_failure`) puts the job back to `queued` with
`next_attempt_at = now() + min(30 s, 1 s × 2^(attempt−1))` plus up to 10 % jitter. After
`WORKER_MAX_ATTEMPTS = 5` the job becomes `dead` and the order `failed`; stock stays reserved for
an operator.

**Delivery is at-least-once** (a job can be retried or reclaimed). **The business effect is
exactly-once**, because the claim is conditional, completion re-checks ownership, and the receipt
key forbids a second completion.

### 4. Isolation level

READ COMMITTED (the Postgres default) is enough. Every critical step is a single conditional
write that Postgres re-evaluates on the newest committed row under a row lock: the `INSERT ... ON
CONFLICT`, the `UPDATE ... WHERE available >= qty`, and the claim `UPDATE`. We never read a value
in one statement and act on it in another.

### 5. Redis is deferred

Redis was planned as a wake-up signal only (never storage), selectable with `QUEUE_BACKEND=redis`.
We deferred it to protect the hard gates. Redis runs in Compose and Kubernetes but nothing uses
it: `QUEUE_BACKEND=postgres` everywhere. Because every job is in Postgres, adding Redis later
cannot change correctness; it would only cut the up-to-2 s polling delay.

## Alternatives considered

| Alternative | Why not |
| --- | --- |
| Lock in Python (`threading.Lock`, a dict of seen keys) | Exists only inside one process. With 2 API replicas both would create an order; lost on restart. Fails gate 1 and E08. |
| `SELECT available`, then `UPDATE` if enough | Two transactions can both read 1 and both subtract (lost update). Needs explicit locking to be safe; the conditional `UPDATE` does it in one statement. |
| `SERIALIZABLE` isolation | Correct, but turns contention into serialization failures that every request must retry. Unnecessary when each step is already one conditional statement. |
| Redis (or another broker) as the job queue | Two systems to keep consistent: an order committed in Postgres but not enqueued (or the reverse) is lost or duplicated. Would need an outbox anyway. |
| Restock automatically when an order fails | Explicitly forbidden by the assignment: failed orders must stay auditable for manual review. |
| Release a job when a worker crashes, via a heartbeat table | More moving parts. An expiring lease gives the same recovery with one column. |

## Consequences

**Positive**

- The four guarantees hold across replicas, restarts and crashes. Evidence: E04 (public checker
  15/0/0), E05 (8 same-key requests over 2 replicas → 1 order, stock −1), E06 (N + 5 buyers for N
  units → exactly N accepted, stock 0), E08 (same order after an API restart), E09 (worker
  SIGKILLed mid-job → reclaimed, `attempts = 2`, 1 receipt), E10 (poison job → 5 attempts, `dead`,
  stock kept).
- The design is small enough to explain line by line: no ORM, no broker, raw SQL in two files.
- Readiness can check the database directly (`/health/ready`), so Kubernetes routes traffic only
  to pods that can commit orders.

**Negative / accepted trade-offs**

- Postgres is a single point of failure. If it is down, orders get `503` and pods go unready, but
  nothing committed is lost. Production would use a replicated or managed Postgres with backups.
- Polling adds up to 2 s before a worker starts a job, and an idle worker queries the database
  every 2 s. The Redis signal would remove this.
- A crashed worker's job waits for its 20 s lease to expire before another worker reclaims it
  (E09: reclaimed 19 s after the kill, completed 8 s later).
- Stock of failed orders stays reserved until an operator acts; there is no admin action to
  release it yet.
- `request_hash` compares whole payloads, so a client that changes anything (even a quantity) must
  use a new key.
